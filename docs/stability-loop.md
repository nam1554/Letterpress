# 안정성 개선 루프

기능과 코드 안정성을 위해 반복하는 절차와, 지금까지 각 바퀴가 **실제로 무엇을
찾았는지**의 기록. 다음 사람이 이어서 돌릴 수 있도록 남긴다.

## 절차

한 바퀴 = **측정 → 판정 → 수정 → 검증 → 커밋**.

1. **측정** — 축을 하나 골라 실제로 돌려 본 수치나 재현 절차를 만든다.
   의견에서 시작하지 않는다. 이 저장소는 이미 그 값을 치렀다: 품질 게이트를
   마크업 추측으로 만들었다가 두 세대를 버렸다(`AGENTS.md`의 게이트 절 참고).
2. **판정** — 재현되는가? 재현 안 되면 결함이 아니다.
3. **수정** — 실패하는 테스트를 **먼저** 쓴다. 브라우저·CLI가 필요해서 테스트가
   불가능하면 그 장치를 순수 함수로 빼서 테스트한다.
4. **검증** — `pnpm exec vitest run` + `tsc --noEmit` + `eslint .`
5. **커밋** — 결함 하나에 커밋 하나. 메시지에 **무엇을 재서 알았는지** 쓴다.

**종료 조건: 측정된 결함 없이 두 바퀴 연속이면 멈춘다.** 억지로 고칠 것을
만들지 않는다.

## 축

① 테스트 없는 모듈 · ② 에러 경로 · ③ 알려진 플레이크 · ④ 타입 구멍 ·
⑤ 리소스 누수 · ⑥ API 경계

### 2바퀴에서 나온 것 (가장 값어치 있었음)

`measureHtmlFiles`가 호출마다 Chrome을 띄우는데 **호출자를 아무도 직렬화하지
않았다.** 동시 실행 한도가 잡 여러 개를 허용하므로 그것들이 비슷한 시각에
끝나면 인스턴스가 겹친다. 느려지는 문제로 끝나지 않는다 — 경쟁으로 launch가
실패하면 "판정 불가"가 되고, 게이트가 그것을 경고로 낮추면서 **반-우회 검사
3종이 통째로 꺼진다.** 머신이 잠깐 붐볐다는 이유로 스크린샷 빌드가 통과할 수
있었다.

덧붙여 그 실패를 `no-chrome`으로 보고하고 있었다. 거기 도달하려면
`findChrome()`이 이미 경로를 찾은 뒤이므로 "Chrome을 찾지 못함"은 거짓이고,
진단 파일을 받은 담당자를 설치 안내로 보낸다. `launch-failed`로 분리했다.

### 틀린 가설도 기록해 둔다

2바퀴의 직렬화가 `AGENTS.md`의 `acceptance.test.ts` 플레이크도 고칠 것이라고
짐작했다. **아니었다.** 확인해 보니 브라우저를 띄우는 테스트 파일은 그 하나뿐이고
케이스도 순차 실행이라 애초에 동시 launch가 없었다. 그 플레이크는 스위트 전체의
CPU·메모리 압박에서 온다. 같은 길로 다시 "고치려" 들지 않도록 `measure.ts`와
`AGENTS.md` 양쪽에 적어 뒀다.

## 기록 (2026-08-07, 2회차)

전 회차의 "다음 바퀴에 볼 만한 것" 중 **디스크 쓰기 실패** 축.
`persist()`(job.json 원자적 쓰기)의 실패를 `writeFile` 주입(ENOSPC)과
디렉터리 권한(EACCES)으로 재현했다. **결함 3건.**

| # | 결함 | 재현 | 수정 |
|---|---|---|---|
| 1 | reconcile 중 persist가 실패하면 `getJob`이 **null** — job.json이 멀쩡히 읽히는데도 잡이 홈 목록·상세에서 통째로 사라진다. 홈이 5초마다 폴링하므로 디스크 문제 동안 stale 잡 전부가 증발하고, `listJobs` 경유 시 unhandled rejection까지 관찰됨 | `store-persist-failure.test.ts` | 판정(러너 없음 = 실패)은 메모리로 돌려주고 persist는 다음 읽기가 재시도. 이벤트 기록은 persist 성공 시에만 — 실패 동안 폴링마다 에러 줄이 쌓이면 안 된다 |
| 2 | ENOSPC가 부분 기록한 `.tmp`가 잡 디렉터리에 실패마다 하나씩 쌓인다 | 〃 | persist 실패 시 tmp를 best-effort로 치우고 다시 던진다 |
| 3 | 러너 catch 블록의 종료 기록(`updateJob`)이 또 실패하면 `emit`이 스킵 — 열려 있던 SSE 화면은 "실행 중"에 영영 멈추고 비동기 블록은 unhandled rejection | `runner.test.ts` "emits a terminal event even when the final persist fails" | 종료 기록은 `.catch(() => {})` — 이벤트·알림·정리는 계속한다. 파일에 남은 running은 재시작 후 reconcile이 정리 (결함 1 수정과 맞물려 실패로 표시됨) |

관찰했지만 고치지 않은 것: `createJob`의 persist가 실패하면 빈 잡 디렉터리가

해결되며, 고아 디렉터리는 어디에도 표시되지 않아 실해가 없다.

## 기록 (2026-08-07, 3회차)

전 회차 백로그의 **SSE 클라이언트 재연결** 축. 앱이 아니라 **브라우저의
EventSource 동작 자체**를 실제 Chrome(puppeteer + 죽였다 살리는 SSE 서버)으로
쟀다. **빈손 — 측정된 결함 없음.**

- **연결 거부(서버 재시작)**: onerror가 readyState 0(CONNECTING)으로 반복
  발화하며 브라우저가 무한 재시도. 서버가 살아나면 자동 재연결(`open` 재발화).
  잡 페이지의 `onopen = () => setEvents([])` + 서버 리플레이 + 라우트의
  `STALE_GRACE_MS` 재확인과 맞물려 재시작 시나리오는 회복된다.
- **비-200 응답(500 실측)**: readyState 2(CLOSED)로 **재시도 없이 영구 종료**
  (서버 요청 수 1). 다만 이 앱의 events 라우트가 비-200을 주는 유일한 현실
  경로는 삭제된 잡의 404뿐이고, 없어진 잡의 스트림이 죽는 것은 올바른 동작이다.
  dev 모드 컴파일 오류 500은 개발자 시나리오라 새로고침으로 족하다.

교훈: 클라이언트에 자체 재연결 로직이 "없는" 것은 결함이 아니었다 — 브라우저
내장 재시도가 이미 그 역할을 하고, 굳이 얹으면 리플레이 중복·이중 연결 같은
새 표면만 생긴다.

## 기록 (2026-08-07, 4회차)

전 회차 백로그의 **런처** 축, macOS(`시작하기.command`)부터. **결함 1건.**

- **"이미 실행 중" 감지가 기본 포트만 봐서, 재더블클릭이 같은 `data/` 위에
  두 번째 인스턴스를 띄운다.** 포트 충돌 시 런처는 25253~25262로 비켜서
  시작하는데(정상), 감지(96행)는 25252만 curl했다. 실측 재현: 35252(다른
  프로그램·404) + 25253(앱·health 200) 상태에서 실행 → 25253을 무시하고
  25254에 **실제 서버가 하나 더 떴다**. 파일시스템이 DB인 앱이라 잡 저장·설정
  쓰기가 두 프로세스에서 겹칠 수 있는 상태.
  → 감지를 폴백 범위 전체(`$PORT` + 25253~25262)의 busy 포트 health-probe로
  교체. 재실행: 25253을 찾아 "이미 실행 중"으로 종료(EXIT 0), 기본 경로
  (25252에 앱)도 즉시 감지. `zsh -n` 통과.
  타임아웃은 8초 유지 — health 첫 호출은 Chrome 탐색(lsregister) 때문에 2초를
  넘을 수 있어, 짧게 잡으면 멀쩡한 앱을 못 알아보고 같은 결함이 재발한다.

**Windows(.ps1)에 동일 결함 확인** (123~126행: `$Port`만 health 확인, 131행
폴백 스캔은 무검사). 이 머신에 pwsh가 없어 규정된 검증(파서 + ScriptAnalyzer +
스텁 하네스)이 불가능해 무검증 수정 대신 다음 바퀴로 넘긴다.

## 기록 (2026-08-07, 5회차)

4회차에서 확인만 해 둔 **Windows 런처(.ps1)의 동일 결함**(기본 포트만 감지 →
재더블클릭이 이중 인스턴스)을 수정. Windows 실기기 없이 AGENTS.md의 규정
절차대로 검증했다:

- 포터블 pwsh 7.4.6(공식 tarball, 시스템 설치 없음)으로 `Parser::ParseFile`
  통과, UTF-8 BOM 보존(efbbbf) 확인, 커밋 후 CRLF 재정규화.
- **스텁 하네스**(`Get-NetTCPConnection`/`Invoke-WebRequest`/`Start-Process`/
  `Read-Host`/`Wait-Process`/`taskkill` 스텁 + `$env:ComSpec`→`/bin/echo`)로
  4시나리오 전 구간 시뮬레이션: 비켜간 앱 감지(25253에서 "이미 실행 중"),
  기본 감지(25252), 충돌만(25253으로 비켜 시작→준비 완료), 전부 빈 포트
  (25252 시작→준비 완료). 전부 기대대로.
- ScriptAnalyzer: 신규 지적 0 (기존 `Write-Host` 경고 15건은 대화형 콘솔
  런처의 의도적 사용).

하네스에서 얻은 요령: 스텁은 스크립트가 다시 정의하는 함수(PortBusy 등)가
아니라 **그 밑의 cmdlet**을 함수로 가려야 하고, `-ErrorAction`을 받으려면
`[CmdletBinding()]`이 필요하다(없으면 바인딩 오류가 catch로 빠져 netstat
폴백이 도는 등 시나리오가 왜곡된다).
