### R2 — 스트림 (SSE) (`943eb2b`..)

발견 1건 수정 + 라우트 테스트 인프라 확보. 테스트 +3 (62 → 65 pass).

- **결함**: 이탈 감지(`req.signal`) 등록이 리플레이·상태 전송이 **전부 끝난 뒤**에
  있었다. 리플레이는 파일 읽기를 기다리는 구간이라 그 사이 탭이 닫히는 일이
  흔한데, 그러면 등록 코드에 도달하지 못해 해당 연결의 구독이 정리되지 않고
  남는다. 잡이 이미 끝난 뒤라면 깨울 이벤트도 없어 영구 누수.
- **수정**: 이탈 감지를 구독보다 앞으로 옮기고, 이미 abort된 요청은 즉시 반환.
  리플레이·상태 전송의 `enqueue`를 전부 가드하고 `cancel()` 정리 경로를 추가.
- **인프라**: `vitest.config.ts`에 `@/` 별칭 추가 — 라우트 핸들러를 직접
  import해 테스트할 수 있게 됐다 (R4 API 경계 라운드의 전제).
- 리플레이/라이브 경계 중복 제거(`lastSeq`)와 종료 시 스트림 닫힘도 테스트로
  고정했다 — 기존 동작은 정확했다.

### R3 — 품질 게이트 (`22c9bd0`..)

발견 2건, 전부 수정. 테스트 +4 (65 → 69 pass).

- **결함 1 (높음): 이전 실행의 검증 결과가 이번 실행의 증거로 통했다.** 게이트는
  "PASS 여부와 무관하게 검증을 실행한 사실은 요구한다"를 계약으로 내걸었지만,
  edit 잡은 원본 workDir을 통째로 복사해 오고 resume은 같은 workDir을
  재사용한다 — 두 경우 모두 `verify.json`과 증거 이미지가 이미 자리에 있어
  계약이 공허했다. 재현 테스트에서 **아무것도 생성하지 않은 edit 잡이
  `succeeded`로 보고**됐고, UI에는 원본을 설명하는 PASS가 표시된다.
  → `AcceptanceOptions.freshSince`를 추가하고 러너가 이번 시도의 시작 시각을
  넘긴다. 그보다 오래된 `verify.json`은 별도 메시지로 실패 처리되며, 그 문구가
  자동 보수 프롬프트에 그대로 실려 에이전트가 재검증하도록 유도한다.
- **결함 2 (낮음): 0바이트 증거물이 `existsSync`를 통과했다** — compare.py가
  쓰다 죽으면 그렇게 남는다. → 크기 0을 없는 것으로 처리.

  트래버설은 그대로 400.

### R5 — UX 완성도 (`ecb6138`..)

발견 2건, 전부 수정. 테스트 +7 (85 → 92 pass).

- **결함 1 (중): 실패한 요청이 아무 반응 없이 삼켜졌다.** 변경 요청 14곳이 전부

  통일. 절대 throw하지 않고 네트워크 실패·비-JSON 응답·API 에러를 각각 사람이
  읽을 수 있는 문구로 돌려준다. 호출부 14곳 전환.
- **결함 2 (중): 변환 시작·수정 요청에 더블클릭 가드가 없었다.** 제출 중 재진입을

### R7 — 보류분 정리 (`adaa7aa`..)

R1~R6에서 "관찰됐지만 고치지 않은 것"으로 남긴 4건을 재검토해 3건을 수정했다.
테스트 +3 (92 → 95 pass).

- **`reconcile` 동시 읽기가 낡은 상태를 돌려줬다 (중).** 진행 중인 reconcile을
  만난 읽기는 중복 쓰기를 피하려고 원본 잡을 그대로 돌려줬는데, 그건 방금
  실패로 판정된 잡을 **"실행 중"으로 표시**한다는 뜻이다(재현: 동시 읽기 3건이
  `failed, running, running`). 부수적으로 플래그가 제거되지 않아 해당 잡은 이
  프로세스에서 다시는 reconcile되지 않았다. → `Set<string>`을
  `Map<string, Promise<Job>>`로 바꿔 동시 읽기가 **같은 결과를 함께 기다리게**
  하고, 끝나면 항목을 비운다. HMR로 남은 옛 `Set`은 형태를 검사해 교체한다.
- **잡 상세 화면이 최대 10초 창에서 영구히 멈출 수 있었다 (중).** 서버 재시작
  직후 `STALE_GRACE_MS` 안에 접속하면 reconcile이 아직 돌지 않아 죽은 잡도
  "실행 중"으로 오고, SSE 스트림은 영원히 기다린다. 그 화면은 스스로 상태를
  다시 읽지 않으므로 수동 새로고침 외에 복구 경로가 없었다. → 유예가 끝난 뒤
  한 번 `getJob`을 다시 호출하도록 스트림에 일회성 재확인을 건다. 러너가 살아
  있으면 아무 일도 없고, 죽었다면 그 읽기가 reconcile을 돌려 실패 이벤트가
  구독자로 흘러온다. 타이머는 `close()`/`cancel()`에서 정리한다.
- **잡 id 충돌이 조용한 데이터 손실이었다 (낮음).** 확률은 낮지만 충돌하면
  `createJob`이 기존 잡 디렉터리 위에 그대로 덮어썼다. → `reserveJobId()`가
  비어 있는 id를 고를 때까지 재시도한다(주입 가능한 생성기로 테스트).
