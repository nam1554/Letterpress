# 안정성·완성도 개선 루프 설계

- 날짜: 2026-07-29
- 대상: Letterpress (repo: marketing-html-maker)
- 상태 파일: `docs/improvement-log.md`

## 목적

앱은 이미 동작하고 검증도 그린이다. 이 루프의 목적은 새 기능 추가가 아니라
**아직 테스트로 고정되지 않은 영역을 체계적으로 좁혀** 실사용에서 터질 수 있는
결함을 미리 잡는 것이다.

시작 시점 베이스라인 (커밋 `5aee73a`): vitest 57 pass / 3 skip, `tsc --noEmit`
0 에러, `eslint` 0 이슈.

## 루프 구조 — 한 라운드 = 5단계

1. **감사(Audit)** — 백로그 최상단 축 **하나만** 좁게 감사한다. 산출물은
   `파일:라인 + 실패 시나리오` 형태의 후보 목록.
2. **선별(Triage)** — "실제 사용자가 겪을 수 있는가"로 거른다. 이론적 결함은
   버린다. 라운드당 최대 3~5건.
3. **수정(Fix)** — 이슈마다 **실패를 재현하는 테스트를 먼저** 쓰고(빨간불 확인),
   그다음 고친다. 테스트 없이 고치지 않는다.
4. **검증(Verify)** — `pnpm vitest run` · `pnpm exec tsc --noEmit` · `pnpm lint`
   · `pnpm build` 네 가지가 전부 그린이어야 한다. 하나라도 빨간불이면 라운드
   미완료.
5. **기록(Record)** — 커밋 1개 + `docs/improvement-log.md` 갱신(해결분 / 신규
   발견분).

## 축 순서 (리스크 높은 순)

| R | 축 | 감사 대상 |
|---|---|---|
| 1 | 런타임 견고성 | `lib/jobs/runner.ts`, `store.ts` — 타임아웃·취소·재시작 복구·동시성·`seq` 경쟁·디스크 오류 |
| 2 | 품질 게이트 | `lib/jobs/acceptance.ts` + runner의 자동 보수 1회 경로 — 게이트 판정, 보수 재실행 중 취소, verify 파싱 |
| 3 | API 경계 | 라우트 13개 (`resume`·`edit` 포함) — 잘못된 id, 없는 잡, path traversal, 깨진 바디, 상태 충돌(실행 중 resume 등) |
| 4 | 스트림 | SSE `events` 라우트 — 재접속 중복, 클라이언트 조기 종료, 잡 종료 시 스트림 닫힘 |
| 5 | UX 완성도 | 에러/빈/로딩 상태, 복구 경로(재시도·이어서 실행), 키보드·포커스 |
| 6 | E2E | mock 프로바이더로 브라우저 전 경로 1회 통과 |

축은 고정이 아니다. 각 라운드의 기록 단계에서 새로 발견한 항목이 더 위험하면
백로그 순서를 바꾼다.

## 정지 조건

연속 2라운드에서 "고칠 가치 있는 것"이 0건이거나 백로그가 소진되면 종료한다.

## 안전장치

자율 연속 진행이므로 범위를 좁게 못박는다.

- **동작·데이터 포맷·아키텍처를 바꾸는 변경은 하지 않는다.** 그런 수정이
  필요하다고 판단되면 고치지 않고 백로그에 남겨 최종 리포트에 올린다.
- **리팩터링 금지** — 버그 수정과 테스트 추가만. 구조는 이미 정돈돼 있다.
- 커밋은 4종 검증이 전부 그린일 때만. 되돌리기는 커밋 단위로 가능하다.
- 실제 CLI를 호출하는 스모크 테스트는 기본 skip 유지(토큰 비용). 루프는 mock
  프로바이더로만 검증한다.
